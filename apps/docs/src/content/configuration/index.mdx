# How to configure

Configuration is done using the `/etc/mon/config.toml` file. Read more on [TOML](https://toml.io/en/) syntax.

## Distributed agents

`mon` supports running multiple agents across different networks (home, office, cloud, etc.) that all report back to a single website. Each tile is assigned to exactly one agent by name; agents authenticate to the website with a bearer token whose SHA-256 hash is declared in the config.

The TOML file lives on the **website host** only. Agents fetch their job list from the website over HTTP.

### Declaring agents

Each agent gets a block under `[agents.<id>]`:

```toml
[agents.default]
token_hash  = "a665a45920422f9d417e4867efdc4fb8a04a1f3fff1fa07e998e86f7f7a27ae3"
description = "Primary agent"

[agents.office]
token_hash  = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
description = "Office network probe"
```

| Property      | Type   | Description                                        | Required |
| ------------- | ------ | -------------------------------------------------- | -------- |
| `token_hash`  | string | Lowercase 64-char hex SHA-256 of the bearer token. | Yes      |
| `description` | string | Human-readable label for the dashboard.            | No       |

### Generating a token

```bash
# mint a random 32-byte token (give this to the agent as AGENT_TOKEN)
token=$(openssl rand -hex 32)
echo "$token"

# hash it and paste the result into config.toml as token_hash
echo -n "$token" | sha256sum
```

The agent reads the token from `AGENT_TOKEN`, or, when that is not set, from the file named by `AGENT_TOKEN_FILE` (for example a Docker Compose secret mounted at `/run/secrets/agent_token`), which keeps the token out of the container's environment.

The plaintext token is never stored on the website side, only its hash. The agent sends it in an `Authorization: Bearer <token>` header.

### Assigning tiles to agents

Every monitor tile (`host`, `website`, `container`, `github`) accepts a `agent` field:

```toml
[[tiles]]
type    = "host"
key     = "router"
address = "192.168.1.1"
agent  = "default"

[[tiles]]
type    = "host"
key     = "office-nas"
address = "10.0.0.5"
agent  = "office"
```

If omitted, `agent` defaults to `"default"`. Tiles whose `agent` does not match any `[agents.<id>]` block will never be polled.

### Check intervals

Agents check every monitor once a minute by default. Change that for the whole board with `ping_interval_ms` in `[options]`, or for one monitor with `interval_seconds` (a positive integer), which takes precedence:

```toml
[options]
ping_interval_ms = 30000 # check every monitor every 30 seconds

[[tiles]]
type             = "website"
key              = "slow-endpoint"
url              = "https://slow.example.com"
interval_seconds = 300 # but this one every 5 minutes
```

Each monitor is checked on its own schedule, so an interval can be shorter or longer than how often the agent fetches its job list. A new monitor is checked straight away, and a check never starts while the previous check of the same monitor is still running.

The agent fetches its job list every `AGENT_POLL_INTERVAL_SECONDS` (default `60`), so added, removed and changed monitors take effect within that time.

A monitor with no check for 3 minutes, or for three of its intervals if that is longer, shows as unknown (an agent tile as offline). Keep in mind that every check is stored, so short intervals on many monitors grow the database quickly: 40 monitors checked every 6 seconds record about 576,000 checks a day, against 57,600 at the default of a minute.

> Agents older than v0.11.0 ignore both settings and check every monitor once per job-list fetch, every `AGENT_POLL_INTERVAL_SECONDS`. Newer agents do the same with websites older than v0.11.0.

### GitHub tokens

`github` tiles accept a per-tile `github_token` (a GitHub PAT) used to call the Check Runs API. The agent does **not** fall back to an environment variable, so if a `github` tile needs auth, set `github_token` on the tile.

### Fetching jobs from the agent side

A agent polls the website to learn its job list:

```bash
curl -H "Authorization: Bearer $AGENT_TOKEN" -H "X-Agent-Id: default" \
  https://mon.example.com/api/agent/jobs
```

The response is a JSON object whose `tiles` array lists the jobs assigned to that agent. The website answers `401` when the agent id is unknown or the token doesn't match its `token_hash`.

### Migration checklist

Moving an existing single-agent setup to the distributed model:

1. Pick a agent id (start with `default`).
2. Generate a token (`openssl rand -hex 32`).
3. Hash it (`echo -n "$token" | sha256sum`) and add `[agents.default]` with the hash.
4. Add `agent = "default"` to each existing monitor tile, or leave it off since the default is `"default"`.
5. Set `AGENT_TOKEN=<plaintext>` and `AGENT_ID=default` in the agent's environment, and point it at the website URL instead of `CONFIG_PATH`.
6. Restart the agent. It will fetch its job list over HTTP and start posting pings.
